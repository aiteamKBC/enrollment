Editable Programme Modules and PCP Pathways
Date: 2026-11-01
Feature branch: CV-and-Programme-Suitability

Result
Modules are configured in the existing Enrolment form builder, on Programme
Suitability & Modules. The assessment editor remains in place. There is no new
top-level administration page and no module content in CV/Job Description.

The administrator selects ME, MM, APM or PCP. Module names, sessions, credits,
descriptions, order, active status and applicable learner-selectable flags are
editable. Administrators can add modules, add nested submodules, deactivate or
reactivate content and reorder it. PCP pathways additionally support editable
titles, subtitles, descriptions, recognition text, target credits, order, active
status and selection enablement. Additional pathways use stable generated IDs.
Published content is deactivated rather than destructively deleted.

Preview uses the same module renderer as the learner card. PCP preview choices
are local state and never write to a learner. Credit totals are displayed, but
target credits do not introduce mandatory validation or block wizard navigation.

Publishing and draft storage
The programmeModules key is part of the existing Wizard_Form_Layouts JSON and
normal wizard publish transaction/baseVersion check. It is preserved by frontend
layout resolution and existing builder operations. No second publishing system
was introduced. Existing published content stays active while edits are drafts.

The old builder had no persistent server draft. Save Draft now stores only the
modules portion in a private ModuleConfigurationDraft record keyed to the
authenticated administrator. Drafts carry the source wizard version; stale saves
are rejected. Saved drafts can be explicitly restored and reviewed. An older
saved draft is identified as such rather than automatically replacing edits.
Publishing remains the existing Publish changes action for the wizard.

Defaults and validation
The original module lists and stable IDs have moved from frontend source to
backend modules_defaults.json. This is idempotent fallback/seed content only;
existing configurations are not overwritten and no layout is auto-published.
Ordinary content changes require no future source-code edits.

Configuration uses a version 1 schema with existing assessment programme codes
ME_L4, MM_L6, APM_L4 and PCP_L6, not new programme catalogue records. Module IDs
are unique within their containing programme/pathway (including nested items);
the composite pathway/module identity preserves existing reused IDs such as pmp.

Backend validation covers supported programmes, pathway association, stable IDs,
duplicate IDs, parent/child trees and circular references, finite non-negative
credits, non-negative integer sessions/order, boolean flags and schema versions.
Absent PCP session values remain null. There is no fixed module/pathway count
limit; existing request-size limits and a defensive nesting-depth guard apply.
Content omitted from a new publication is retained as inactive. The entire
configuration cannot be cleared with null to bypass historical retention.

Permissions
The existing enrolment authentication/access-grant gate and admissions staff
policy protect defaults, private drafts and publication. Learners cannot write
configuration through these APIs. Learner modules endpoints are read-only and
scoped to the authenticated learner; another learner/employer is refused.
Draft writes use CSRF protection and the existing CSRF retry mechanism.

Historical learner content and selections
Assessment now has nullable modules_configuration and
modules_configuration_version fields. On the first modules access after confirmed
programme selection, the current published modules configuration/version is
copied into that existing learner assessment record. It remains immutable on
later module reads. This follows the existing feature's snapshot/version policy
at the beginning of the modules portion; an assessment's original question
configuration/version and scores are not changed.

Learners who already saved PCP choices before configurable modules existed are
pinned to the original default content with version 0. This preserves original
names, sessions, credits, hierarchy and IDs even if an administrator has already
renamed or deactivated them in a later publication. Pinning is lazy and scoped;
there was no bulk rewrite of historical submissions.

PCP pathway/module IDs remain in the existing Extended_ILR.Wizard_draft JSON,
alongside a configurationVersion marker. Other wizard answers remain in that
same draft. Saves validate the confirmed selected programme, pinned version,
available pathway, module IDs and selection flags. Existing unversioned choices
remain readable and can be upgraded on normal saves. Only the selected pathway's
choices are active; prior choices in other paths remain retained. Module content
comes from the backend snapshot, with active flags/order applied dynamically.

New module enrolments use the current published configuration. Existing module
enrolments retain their pinned content after publishing and refreshing. ME/MM/APM
continue as read-only lists. PCP uses an adaptive grid and supports arbitrary
pathway IDs/counts. All displays use the confirmed selected programme, including
permitted alternative programmes, rather than the recommendation alone.

Existing assessment questions, weights, scoring, recommendation, alternative
reason flow, confirmation, account synchronization, result card, Preview
Assessment, read-only Show Answers, CV fields and qualification labels are reused
without changing their business logic. Existing automatic navigation after
programme confirmation remains intact.
