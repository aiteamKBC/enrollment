Root cause and evidence
1. useModuleSelectionSave called WizardContext.saveIlr after a 200ms debounce. That method sent ILR answers and every other wizard section through the Extended ILR endpoint, which update_or_create locked Extended_ILR and ran per-step projections and their audit hooks inside its transaction.
2. For a complete PCP selection, saveIlr then sent a second PUT to the dedicated modules endpoint. That endpoint locked Assessment and then locked/wrote Extended_ILR again to merge programmeModules into the wizard JSON.
3. Module edits therefore entered long, unrelated ILR transactions twice. Navigation also called saveIlr independently; the hook's local queue did not serialise navigation writes, and it queued captured snapshots instead of replacing obsolete pending work.
4. Real development PostgreSQL query instrumentation confirmed both Extended_ILR SELECT FOR UPDATE statements and UPDATE statements. No PostgreSQL triggers were registered on Extended_ILR/Assessment. ExtendedIlr has audit pre/post-save listeners; Assessment has none. The database aliases use separate connections to the same database identity (their PORT settings differed in representation).
5. Initial pg_stat_activity inspection had no active blocker, so the original production blocking PID/request cannot be identified retrospectively. The application lock path is confirmed. A controlled PostgreSQL test held the synthetic ILR row, observed one blocking backend via pg_blocking_pids, and reproduced the old FOR UPDATE lock failure. The new module endpoint saved successfully while that same ILR row remained locked.

Backend changes
- Reused Assessment, its published modules snapshot and the existing modules GET/PUT endpoint. Added modules_selection and modules_revision to that record; no parallel modules table or dual-write system.
- Assessment.modules_selection is authoritative. Legacy programmeModules JSON remains a compatibility source until copied, and old learner data is not deleted/reset.
- Module saving never writes or row-locks Extended_ILR and never invokes other-step projections, ILR signature updates or ExtendedIlr audit signals.
- One short default-alias transaction locks only Assessment with NOWAIT, validates published snapshot rules, includes mandatory IDs, and updates only feature fields when data changes. No nested pinning savepoint/redundant assessment fetch in the save path.
- Revision comparison rejects distinct stale edits with 409. Identical retries acknowledge the current revision without a write. Concurrent lock ownership returns a safe 503 immediately rather than waiting for a statement timeout.
- Partial pathway/module choices autosave as incomplete. Only server-validated complete choices can complete Step 6. Existing count, credit, hierarchy and mandatory rules are unchanged.
- Logs include learner ID, revision, duration and SQLSTATE on failure; responses contain a user-friendly error without PostgreSQL tuple/query details. There is no unbounded database retry loop and no production timeout increase.
- Completion uses the same saved_choices service, now reading authoritative Assessment data. Legacy reads remain available; refreshed module settings and historical pinned configurations retain their existing behaviour.

Frontend changes
- Immediate local checkbox/credits updates, with a 500ms debounce.
- One provider-owned save queue per wizard learner, surviving module-step unmount/remount. At most one request is in flight; newer pending edits replace obsolete snapshots rather than accumulating a FIFO backlog.
- Module-only PUTs use expectedRevision; saveIlr no longer sends/commits module selections. Module-only edits do not make the generic wizard save dirty.
- Saved responses cannot replace newer local choices. Background refreshes cannot replace unsaved choices or regress an acknowledged revision.
- Revision conflicts refresh server metadata while keeping local choices for explicit retry. Configuration-version failures refresh settings and preserve the existing review-and-save action.
- Saving…, All changes saved., and an actionable error/Retry reflect actual acknowledgement. A failure never marks the selection saved or Step 6 complete.
- Queue failures stop until a new edit or explicit retry; merely leaving an errored step does not start an automatic retry loop. Pending successful-path work flushes on step departure.
- Extended ILR hydration cannot overwrite the module endpoint's authoritative selection.
